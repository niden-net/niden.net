Design Patterns - Registry

design patternsphpprogrammingserieshow-toregistry

Continuing the design patterns in PHP posts, we are going to focus today on the Registry pattern and how we are using it in Phalcon. In the Gateway post we put each payment provider behind one interface. Today we will use a registry to pick the right provider by name, while the application runs.

The pattern in one paragraph

A registry is a well-known object that other objects use to find common objects and services. You store an object, or a factory that builds it, under a name once. Any code that knows the name gets the same object back. Most registries keep two maps: one with the definitions and one with the instances already built. The first request for a name builds the object, and every request after that gets the cached one.

Why we use it

  • One place to look. Shared objects such as the configuration, the database connection or the logger live behind one known name, not in globals scattered around the code.
  • Lazy construction. Store a factory, not an object. Nothing is built until the first request asks for it, so a request that never sends an email never builds the mailer.
  • Choice by name, at runtime. When the object you need depends on data (the payment provider the customer picked, the database replica to read from, the sanitizer a form field asks for), a registry turns a string into the right object without a switch statement.
  • Easy to replace. A test sets a fake under the same name, and the code that asks for it does not change.

Rules and gotchas

  • Phalcon\Support\Registry keys are case-insensitive. $registry->Locale and $registry->locale are the same entry. The Collection it extends can be case-sensitive, but the Registry constructor does not expose that flag.
  • A stored null reads as the default. After $registry->set('discount', null), has('discount') is true, but get('discount', 10) returns 10. Use has() when null means something.
  • An unknown key is not an error. Phalcon\Support\Registry returns null (or your default) for a name nobody set, so a typo goes unnoticed. Filter, FormsLocator and ConnectionLocator throw FilterNotRegistered, FormNotInLocator and ConnectionNotFound. For services, use a registry that throws.
  • Registry is final. You cannot extend it to add types. Wrap it, or write a typed registry like the one above.
  • The first Di wins. The constructor sets the default container only when there is none. A second new Di() does not replace it. Call Di::setDefault() when you want to switch, and Di::reset() between tests.
  • A new definition does not replace a built shared instance. After getShared('mailer'), a second setShared('mailer', ...) still gives you the old object. Call removeShared('mailer') to drop the instance and keep the definition, or remove('mailer') to drop both. Filter::set() and FormsLocator::set() clear the cached instance for you.

What it costs

A registry is easy to add and hard to remove later. The convenience is not free:

  • Hidden dependencies. A class that calls Di::getDefault() in a method does not list what it needs. You find out at runtime, for example with ModelOrmServicesUnavailable when there is no container. This is why the OrderProcessor receives the registry instead of looking for it.
  • Global state in tests. The default container is static, so it lives longer than a test. A service that one test registers is still there in the next one, unless tearDown() calls Di::reset().
  • Names are strings. A typo in a name is a runtime error, not a parse error. Class-name keys (GatewayRegistry::class) or class constants let your IDE and the static analyzers find them.
  • The grab bag. A registry that holds the configuration, the logger, the current user and the cart makes every class that touches it depend on all of them.

Rule of thumb: keep each registry to one type of thing, pass it in through the constructor, and leave the static access point to framework code that cannot get a constructor parameter, such as models.

When not to reach for it

  • The choice is fixed when the application starts. If each deployment uses one payment provider, inject that one gateway. A factory picks it from the configuration once (the option we mentioned at the end of the Gateway post), and nothing looks it up by name after that.
  • You want fewer constructor parameters. Passing a registry so that a class can pick what it needs is a service locator. The dependencies are still there, you just cannot see them.
  • The value belongs to one request, but the registry lives longer. In a long-running worker (Swoole, RoadRunner, FrankenPHP in worker mode), a shared registry survives between requests. The tenant or the user from the last request is still in it.

Elsewhere in the framework

  • Phalcon\Filter\Filter maps sanitizer names to classes (Filter::getDefaultMapper()). set() adds or replaces one, and the instance is built on first use.
  • Phalcon\Forms\FormsLocator holds two registries: named forms, cached when no entity is passed, and the element types that Form::load() uses. setElement() adds your own element type.
  • Phalcon\DataMapper\Pdo\ConnectionLocator keeps registries of read and write connections. getRead() without a name picks a random read connection, and with no read connections it returns the master connection.

Takeaway

A registry is a map with a name on the door. Phalcon uses the same small shape in many places: a map of definitions, a map of instances, and a build on the first request. Use one when the code picks an object by name while it runs. Keep it typed, keep it to one kind of thing, and pass it in instead of reaching for it.
